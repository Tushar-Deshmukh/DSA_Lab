## How this week fits together

Last week every edge cost the same, so BFS layers were distances. This week edges have weights, sets of nodes merge as edges arrive, and some problems can be solved by a single sequence of locally best choices. The common thread is **proving** that a simple rule is safe: "the popped node is final" (Dijkstra), "the cheapest edge between two trees is safe" (MST), "the earliest-ending interval can always be kept" (greedy).

## From BFS to weighted shortest paths {theory}

BFS works on unweighted graphs because nodes leave the queue in order of distance. With weights, the order in which nodes are discovered no longer matches their distance: a path of three cheap edges can beat one expensive edge. Dijkstra restores the "process in order of distance" idea by replacing the queue with a min-heap keyed by tentative distance.

## Changing the cost function (Stretch: 1631) {theory}

Dijkstra only needs one thing from the path cost: extending a path never makes it cheaper. Sums of non-negative weights satisfy that, and so does "the largest single step so far". Problem 1631 (Path With Minimum Effort) asks for the route whose **largest** height difference is smallest, so the relaxation becomes `max(d, |h[next] − h[cur]|)`.

## Kruskal: cheapest safe edge first {theory}

@pull Minimum spanning tree (MST)

Why is taking the cheapest edge between two different trees always safe? Split the vertices into any two groups (a *cut*). Every spanning tree needs at least one edge crossing the cut. If an MST used a more expensive crossing edge, swapping it for the cheapest crossing edge keeps the tree connected and does not raise the total. This *cut property* is an exchange argument, the same reasoning you will use for greedy proofs tomorrow.

## Prim for complete graphs (1584) {theory}

In 1584 every pair of points is an edge, so E ≈ n²/2. Kruskal would sort all of them (O(n² log n)), and a heap-based Prim pushes O(n²) entries (also O(n² log n)). Prim's array version keeps `best[v]`, the cheapest known connection from each outside point to the tree, and each round scans that array once: O(n²) total, with no heap and no edge list.

## When Dijkstra's assumption breaks (Optional: 787) {theory}

Problem 787 asks for the cheapest flight route using **at most k stops**. Dijkstra finalises each city at its cheapest cost, but the cheapest way to reach an intermediate city might use too many stops, while a pricier route with fewer stops is the one that can still reach the destination in time. The fix is to count flights explicitly: run k + 1 rounds of relaxation, each reading only the previous round's distances.

## Forced choices (Stretch: 846) {code}

In Hand of Straights the smallest card left has no smaller neighbour, so it **must** start a group. That forced choice removes all guessing: take it, consume the next `groupSize − 1` consecutive values from a count map, and repeat.

```ex
type: code
tag: Hand of Straights (846)
q: "Write `isNStraightHand(hand, groupSize)`: can the cards be split into groups of `groupSize` consecutive values?"
fn: isNStraightHand
starter: |
  function isNStraightHand(hand, groupSize) {

  }
solution: |
  function isNStraightHand(hand, groupSize) {
    if (hand.length % groupSize !== 0) return false;
    const count = new Map();
    for (const c of hand) count.set(c, (count.get(c) || 0) + 1);
    for (const c of [...count.keys()].sort((a, b) => a - b)) {
      const k = count.get(c);
      if (k === 0) continue;
      for (let v = c; v < c + groupSize; v++) {
        if ((count.get(v) || 0) < k) return false;
        count.set(v, count.get(v) - k);
      }
    }
    return true;
  }
tests:
  - { args: [[1, 2, 3, 6, 2, 3, 4, 7, 8], 3], expect: true }
  - { args: [[1, 2, 3, 4, 5], 4], expect: false }
  - { args: [[1, 1, 2, 2, 3, 3], 3], expect: true }
  - { args: [[5], 1], expect: true }
  - { args: [[8, 10, 12], 3], expect: false, hidden: true }
  - { args: [[1, 1, 2, 3], 2], expect: false, hidden: true }
  - { args: [[1, 2, 3, 3, 4, 5], 3], expect: true, hidden: true }
explain: "Starting k groups at once (k = the count of the smallest card) makes it O(n log n) for the sort plus O(n · groupSize) worst case for the scan."
hints:
  - "Which card is forced to start a group?"
  - "Keep counts in a Map and walk the distinct values in sorted order."
  - "If the smallest card appears k times, k groups start there."
```

      for (let k = 0; k < 3; k++) got[k] = Math.max(got[k], t[k]);
