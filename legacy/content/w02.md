## The three words that decide the pattern {theory}

Before any algorithm, read the problem's nouns carefully. Most contiguous-range problems this week turn on one distinction:

@pull Subarray vs substring vs subsequence

Take `[3, 1, 2]`. Its subarrays are `[3] [1] [2] [3,1] [1,2] [3,1,2]`: six, which is n(n+1)/2 for n = 3. Its subsequences also include `[3, 2]`, which skips the 1: there are 2³ = 8 including the empty one. When a problem says "contiguous", "window", "substring" or "subarray", the search space is at most quadratic and a linear pattern is likely. When it says "subsequence", expect exponential brute force and DP or greedy.

## Intuition: sorted order tells you which end to throw away {theory}

You want two numbers from a sorted list that add up to a target. Picture holding the smallest and the largest number. Add them.

- If the sum is **too small**, the smallest number is hopeless: it is already paired with the biggest partner available, and that was not enough. Every other partner is smaller. Throw the smallest number away.
- If the sum is **too large**, the largest number is hopeless for the mirror reason. Throw it away.
- If the sum is exactly right, you are done.

Each comparison removes one number from consideration *forever*, so with n numbers there are at most n − 1 comparisons. Nothing here needs extra memory.

@pull Two pointers

## Definition and the invariant {theory}

**Opposite-end two pointers**: indices `l` and `r` start at the two ends of a sorted (or symmetric) sequence and move toward each other. At every step a rule moves exactly one of them, and the rule is justified by an argument that the element being passed over cannot belong to any answer.

The **invariant** that makes it correct: *if an answer exists, it lies inside `[l, r]`.* It is true at the start (the whole array), and each move keeps it true because the discarded index provably cannot be part of an answer. When `l` meets `r`, the range has no pairs left, so no answer exists.

:::key The one sentence to remember
When `numbers[l] + numbers[r] < target`, `numbers[l]` is too small **even with its largest possible partner** (`numbers[r]`), so no pair using index `l` can work. When the sum is too big, `numbers[r]` is too big even with its smallest partner.
:::

## See it: the pair grid {visual}

The grid below lists every pair (i, j) with i < j and shows its sum. Because the array is sorted, sums grow to the right along a row and downward along a column. The brute force checks cells one at a time; two pointers start at the top-right corner and delete a whole row (`l++`) or a whole column (`r--`) with each comparison.

## The code, line by line {code}

```anno
title: "Two Sum II (problem 167), returning 1-based indices"
code: |
  function twoSumSorted(numbers, target) {
    let l = 0, r = numbers.length - 1;
    while (l < r) {
      const sum = numbers[l] + numbers[r];
      if (sum === target) return [l + 1, r + 1];
      if (sum < target) l++;
      else r--;
    }
    return [];
  }
notes:
  2: Start with the widest range. `r` is the last valid index, `length - 1`.
  3: "`<`, not `<=`: a pair needs two different indices. When `l === r` only one element is left."
  4: The only work per step. No inner loop, so the loop body is O(1).
  5: The problem numbers positions from 1, hence `+ 1`. Returning `[l, r]` is the most common slip on this problem.
  6: Too small even with the largest partner → discard the left value.
  7: Too large even with the smallest partner → discard the right value. `else` covers `sum > target` because equality returned on line 5.
  9: Unreachable on LeetCode 167 (a solution is guaranteed) but keeps the function total for other inputs.
```

## Complexity, derived {complexity}

Count the loop iterations, not the lines. Every iteration either returns or moves one pointer one step inward, so the gap `r − l` shrinks by exactly 1 per iteration. It starts at n − 1 and the loop stops at 0: **at most n − 1 iterations, each O(1), so O(n) time.** The only memory is `l`, `r` and `sum`: **O(1) extra space.**

Compare the alternatives for a sorted input:

| Method | Time | Extra space | Notes |
| --- | --- | --- | --- |
| Brute force, every pair | O(n²) | O(1) | ignores sorted order |
| Binary search for each partner | O(n log n) | O(1) | uses order, but only half of what it tells you |
| Hash map (problem 1) | O(n) | O(n) | needed when input is unsorted |
| Two pointers | O(n) | O(1) | best when input is already sorted |

## Trade-offs and when not to use it {tradeoffs}

Two pointers needs a reason to discard an end. Sorted order gives one; symmetry (palindromes) gives one. Without it, the moves are guesses. The most important counter-example is the problem you solved in Week 1:

:::warn Two Sum (problem 1) is not a two-pointer problem
The input is unsorted and the answer is a pair of **original** indices. Sorting would cost O(n log n) and scramble the indices, so you would need to sort `[value, index]` pairs and map back. A hash map does it in one O(n) pass. Reach for two pointers when the input is *already* sorted, or when sorting loses nothing you need.
:::

| Situation | Use | Why |
| --- | --- | --- |
| Sorted, find a pair with sum / difference | Two pointers | O(n), O(1) space |
| Unsorted, return original indices | Hash map | sorting would lose the indices |
| Unsorted, return the values, or count pairs | Sort + two pointers, or hash map | both O(n log n) / O(n); two pointers saves memory |
| Need every pair | Neither helps | the output alone is O(n²) |

## Pattern recognition {pattern}

@pull Pattern 2.1

:::mistake Mistakes that cost the most time
- Writing `while (l <= r)` for a pair search: when `l === r` you pair an element with itself.
- Returning 0-based indices on problem 167, which asks for 1-based ones.
- Skip loops (`while (!isAlnum(s[l])) l++`) without `l < r`: they run off the end on `" .,"`.
- Building a cleaned string with a regex first. It works, but uses O(n) space and is not what interviewers want to see when they ask for O(1).
- Comparing `'0'` and `'P'` case-insensitively by mistake: digits must be kept as they are.

```ex
      if (a > b) { out[k] = a; l++; }
```

## Stretch: from 2-sum to 3Sum {stretch}

3Sum (problem 15, today's Stretch) reduces to the code above: sort, fix `nums[i]`, then run two pointers on the rest for target `−nums[i]`. The new difficulty is duplicates. After sorting, equal values are adjacent, so skip `i` when `nums[i] === nums[i − 1]`, and after recording a triplet move both pointers past equal values. Complexity: O(n log n) to sort plus n scans of O(n) = **O(n²)**, which is optimal for listing all triplets in the worst case.

```ex
type: mcq
tag: Stretch check
q: "In 3Sum, after sorting `[-1, 0, 1, 2, -1, -4]` to `[-4, -1, -1, 0, 1, 2]`, why do we skip `i = 2`?"
options:
  - t: Because `nums[2] === nums[1]`, every triplet starting with it was already found from `i = 1`.
    ok: true
    why: Fixing the same value twice would list the same triplets again.
  - t: Because negative numbers cannot be the smallest element of a triplet summing to 0.
    why: "`-1` is the smallest element of `[-1, 0, 1]`."
```

## Same-direction pointers: the Dutch national flag {theory}

Yesterday both pointers walked *towards* each other. Same-direction pointers walk the *same* way and split the array into regions that each mean something. You met the simplest version in Week 1 (Move Zeroes: a write pointer behind a read pointer). Sort Colors needs three groups, so it needs three pointers.

@pull Pattern 2.2

Picture the array as four regions, always in this order:

| region | indices | contains |
| --- | --- | --- |
| zeros | `[0, low)` | only 0s, final |
| ones | `[low, mid)` | only 1s, final |
| unknown | `[mid, high]` | not yet examined |
| twos | `(high, n − 1]` | only 2s, final |

At the start, everything is unknown (`low = mid = 0`, `high = n − 1`). Each step looks at `nums[mid]`, the first unknown value, and moves it into the right region. When the unknown region is empty (`mid > high`), the array is sorted.

@viz dutch-flag

:::key Why `mid` does not move after a swap with `high`
When `nums[mid]` is 2, you swap it with `nums[high]`. The value that arrives at `mid` came from the *unknown* region, so nobody has looked at it yet. It might be a 0 or a 2. Advancing `mid` would leave it unclassified. A swap with `low` is different: the value arriving from `low` is from the 1s region (or it is the same element when `low === mid`), so it is already known to be a 1.
:::

## Proving a pointer move: Container With Most Water {theory}

Problem 11 looks like yesterday's pair search, but there is no target. You want the pair of walls `(l, r)` that maximises `min(h[l], h[r]) × (r − l)`. Start with the widest pair. Which wall should move?

The area is capped by the **shorter** wall. Suppose `h[l] < h[r]`. Every other container that uses wall `l` is *narrower* (its right wall is closer) and still capped at height `h[l]` or lower. So none of them can beat the current area. Wall `l` has nothing left to offer: discard it. Moving the taller wall could never help, because the shorter wall would still be the cap while the width shrinks.

## Kadane's algorithm, derived {theory}

@pull Kadane's algorithm

You will not memorise Kadane. You will derive it, because the derivation is the reusable part.

:::stages Maximum Subarray (problem 53), from brute force to one pass
@stage problem Understand the problem
Given `nums`, find the contiguous subarray with the largest sum and return the sum. `nums = [-2, 1, -3, 4, -1, 2, 1, -5, 4]` → 6, from `[4, -1, 2, 1]`. Constraints allow n up to 10⁵, so O(n²) (10¹⁰) is too slow and the target is O(n) or O(n log n).

@stage naive Naive approach
Try every start `i` and every end `j ≥ i`. Summing each subarray from scratch is O(n³). Keeping a running sum as `j` grows makes it O(n²):

```js
function maxSubArrayBrute(nums) {
  let best = -Infinity;
  for (let i = 0; i < nums.length; i++) {
    let sum = 0;
    for (let j = i; j < nums.length; j++) {
      sum += nums[j];              // sum of nums[i..j]
      best = Math.max(best, sum);
    }
  }
  return best;
}
```

@stage insight Discover the optimisation
Turn the loops around: fix the **end** `j` instead of the start. Ask: *what is the best subarray that ends exactly at j?* It either

- is just `[nums[j]]`, or
- extends the best subarray ending at `j − 1` by one element.

Nothing else is possible: any subarray ending at j that is longer than one element consists of a subarray ending at j − 1, plus `nums[j]`, and the best such one uses the best subarray ending at j − 1. So

`bestEnding[j] = max(nums[j], bestEnding[j − 1] + nums[j])`

and the answer is the largest `bestEnding[j]` over all j. In words: **if the best sum ending just before here is negative, drop it and start fresh**.

| j | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| nums[j] | −2 | 1 | −3 | 4 | −1 | 2 | 1 | −5 | 4 |
| bestEnding[j] | −2 | 1 | −2 | 4 | 3 | 5 | **6** | 1 | 5 |
| choice | start | restart | extend | restart | extend | extend | extend | extend | extend |

Each value needs only the previous one, so the table collapses into a single variable `cur`.

## The idea {theory}

@pull Sliding window

Brute force over contiguous ranges looks at all O(n²) windows and recomputes each one. A sliding window keeps a **running state** (a sum, a count map, a set) for the current window `[l, r]` and updates it in O(1) when an edge moves. The total work is O(n) because `r` moves n times and `l` moves at most n times, *in total*, not per step.

:::key The amortised argument
An inner `while` inside a `for` loop does **not** automatically mean O(n²). Count how many times `l++` can run over the whole algorithm: `l` only increases and never passes n, so at most n times. The two loops together do at most 2n pointer moves.
:::

## Variable-size windows {theory}

Most window problems ask for the longest or shortest window that satisfies a condition. The window grows until it becomes invalid, then shrinks from the left until it is valid again. The roadmap's general template (reference 6.10):

```js
function longestWindow(arr) {
  let l = 0, best = 0;
  const state = new Map();              // whatever describes the window
  for (let r = 0; r < arr.length; r++) {
    // 1. add arr[r] to state
    while (/* window [l, r] is invalid */ false) {
      // 2. remove arr[l] from state
      l++;
    }
```

## The precondition: monotonicity {theory}

A window is allowed to throw away its left end forever only if validity behaves *monotonically*:

- for "longest window with at most …" problems: if `[l, r]` is invalid, then every longer window `[l, r']` with `r' > r` is also invalid, so `l` must move and never needs to come back;
- for "shortest window with at least …" problems: if `[l, r]` is valid, growing it keeps it valid, so once it is valid you shrink to find the minimum.

With non-negative numbers, adding elements never decreases a sum, so sum conditions are monotone. With **negative numbers**, adding an element can decrease the sum, and the rule "grow until too big, then shrink" has no meaning. That is the moment to switch to prefix sums (Friday).

## Fixed windows of counts {theory}

Permutation in String (567) asks whether some window of `s2` is an anagram of `s1`. A window of length `|s1|` is an anagram exactly when its letter counts equal `s1`'s counts. So: build `need` once, slide a window of the same length over `s2`, and update the window's counts as letters enter and leave.

@viz win-perm

The visualizer compares all 26 counts at every step. That is O(26) per step, which is fine: O(26 · n) is O(n). The faster version keeps a number `matches` = how many of the 26 letters currently have equal counts. When a letter enters or leaves, only that letter's equality can change, so `matches` is updated in O(1), and the window is a permutation when `matches === 26`.

## Shortest valid window {theory}

Minimum Size Subarray Sum (209): the shortest subarray of positive numbers with sum ≥ target. Positive numbers make validity monotone: growing a valid window keeps it valid. So grow `r` until the window is valid, then **shrink as long as it stays valid**, recording the length at each valid moment.

@viz win-min

:::key Where the answer is recorded
For a *longest* window, you record after the `while` (the loop restores validity). For a *shortest* window, you record **inside** the `while`, because the loop runs only while the window is valid, and the moment it exits, the window is invalid.
:::

## The hardest standard window: Minimum Window Substring (Optional) {stretch}

Problem 76 combines today's two ideas. Count what `t` needs. Keep `missing` = how many required characters the window still lacks (start at `t.length`). Adding a character that is still needed decrements `missing`. When `missing === 0` the window covers `t`: record it and shrink from the left while it still covers. Removing a character the window needed re-increments `missing`.

```js
function minWindow(s, t) {
  const need = new Map();
  for (const c of t) need.set(c, (need.get(c) ?? 0) + 1);
  let missing = t.length, l = 0, bestL = 0, bestLen = Infinity;
  for (let r = 0; r < s.length; r++) {
    const c = s[r];
    if (need.has(c)) { if (need.get(c) > 0) missing--; need.set(c, need.get(c) - 1); }
    while (missing === 0) {                       // window covers t: record, then shrink
      if (r - l + 1 < bestLen) { bestLen = r - l + 1; bestL = l; }
      const d = s[l++];
      if (need.has(d)) { need.set(d, need.get(d) + 1); if (need.get(d) > 0) missing++; }
    }
  }
  return bestLen === Infinity ? '' : s.slice(bestL, bestL + bestLen);
}
```

`need.get(c)` going negative means the window holds extra copies of `c`; those can be removed without breaking coverage, which is exactly what the `> 0` checks express.

## Prefix sums + hash map: counting exact sums {theory}

Subarray Sum Equals K (560) asks how many subarrays sum to exactly k, with negatives allowed. Write the condition in prefix terms: subarray `[j..i]` sums to k exactly when `pre[i+1] − pre[j] = k`, that is, when **an earlier prefix equals `cur − k`**, where `cur` is the running sum. That is Two Sum on prefix sums: as you walk, look up how many earlier prefixes equal `cur − k`, then record `cur`.

@pull Example 3

@viz prefix-map

:::key Why `{0: 1}`
The empty prefix (sum 0, before any element) is a real prefix. It is what lets a subarray start at index 0: when `cur` itself equals k, you need `cur − k = 0` to have been "seen once". Without the seed, `[3]` with k = 3 would return 0.
:::

## Prefix and suffix products (Stretch) {theory}

Product of Array Except Self (238) forbids division. The product of everything except `nums[i]` is (product of everything left of i) × (product of everything right of i). Fill `out[i]` with the left products in one pass, then sweep from the right with a running product:

```js
function productExceptSelf(nums) {
  const n = nums.length, out = new Array(n);
  out[0] = 1;
  for (let i = 1; i < n; i++) out[i] = out[i - 1] * nums[i - 1];   // product of nums[0..i-1]
  let right = 1;                                                    // product of nums[i+1..n-1]
  for (let i = n - 1; i >= 0; i--) { out[i] *= right; right *= nums[i]; }
  return out;
}
```

## Difference arrays (Optional) {theory}

The reverse problem: many updates "add v to every element in [l, r]", then read the array once. Applying each update directly is O(length) per update. Instead record where each update *starts* and *stops* in a difference array, and let one prefix-sum pass apply them all.

@viz diff-array

```ex

rows:

    why: "diff[1] += 2, diff[4] −= 2; then diff[0] += 5, diff[2] −= 5; then diff[2] −= 1, diff[5] += 1. Slot 2 receives two stops: −5 and −1."
  - prompt: final array
```
