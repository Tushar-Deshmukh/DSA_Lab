## The boundary idea {theory}

@pull Binary search as "find the boundary"

Look at `nums = [1, 2, 2, 2, 5]` and the predicate `nums[i] >= 2`. Across the array it reads `F T T T T`. The predicate is **monotone**: once it becomes true it stays true, because the array is sorted. "Where does 2 first appear?" becomes "where is the first T?", and that question always has an answer: an index from 0 to n, where n means "no T at all".

That reframing is what removes the special cases. You no longer ask "did I find it?" inside the loop. You shrink the range until it pins down the boundary, then check the boundary once, after the loop.

## Two conventions, and how to derive them {theory}

@pull Two interval conventions. Pick one and keep it

The derivation has two parts, and you should be able to say both:

1. **The answer stays in the range.** If `pred(mid)` is true, the first true index is `mid` or earlier, so `hi = mid` keeps it. If false, everything up to `mid` is false, so `lo = mid + 1` keeps it.
2. **The range shrinks.** `mid` is always in `[lo, hi)`, so `hi = mid` makes the range smaller, and so does `lo = mid + 1`. A range that shrinks by at least one every iteration must end.

## Any monotone predicate {theory}

First Bad Version (278) has no array at all: versions 1..n, and an API `isBadVersion(v)` that is false up to some version and true from then on. That is a monotone predicate over `[1, n]`, so the first bad version is `firstTrue(1, n + 1, isBadVersion)`. Recognising the predicate is the whole problem.

## Peaks without sorted data {theory}

Find Peak Element (162) asks for any index whose value is greater than both neighbours, with `nums[−1] = nums[n] = −∞`. The array is not sorted, yet O(log n) is possible. Look at `mid` and its right neighbour. If the right neighbour is larger, you are walking uphill: keep going right and either the values keep rising until the end (the last element is then a peak, because `nums[n] = −∞`) or they fall at some point (the top before the fall is a peak). Either way a peak exists right of `mid`. Otherwise `mid` is a peak or the slope goes up to the left, and by the mirror argument a peak exists in `[lo, mid]`.

```ex
  clarify: |
    - Values can be negative (−100..100), n ≤ 100.
    - Ties by frequency → larger value first.
  brute: "Count occurrences, then sort with a two-key comparator: frequency ascending, then value descending. O(n log n). This is already the intended solution; the work is getting the comparator right."
  optimize: "Precompute counts in a Map so the comparator is O(1). `(a, b) => count.get(a) - count.get(b) || b - a`. Returning numbers, with `||` for the tie-break."
  edges: |
    - all values distinct → sorted descending
    - negative values `[-1,1,-6,4,5,-6,1,4,1]` → `[5,-1,4,4,-6,-6,1,1,1]`
    - single element
  complexity: "O(n log n) time, O(n) space for the counts."
fn: frequencySortNums
starter: |
  function frequencySortNums(nums) {

  }
solution: |
  function frequencySortNums(nums) {
    const count = new Map();
    for (const x of nums) count.set(x, (count.get(x) ?? 0) + 1);
    return nums.sort((a, b) => count.get(a) - count.get(b) || b - a);
  }
tests:
  - { args: [[1, 1, 2, 2, 2, 3]], expect: [3, 1, 1, 2, 2, 2] }
  - { args: [[2, 3, 1, 3, 2]], expect: [1, 3, 3, 2, 2] }
  - { args: [[-1, 1, -6, 4, 5, -6, 1, 4, 1]], expect: [5, -1, 4, 4, -6, -6, 1, 1, 1] }
  - { args: [[7]], expect: [7], hidden: true }
  - { args: [[3, 2, 1]], expect: [3, 2, 1], hidden: true }
explain: "Count once outside the comparator: counting inside it would make each comparison O(n)."
hints:
  - Count first.
  - "Primary key: frequency ascending. Secondary key: value descending."
```
