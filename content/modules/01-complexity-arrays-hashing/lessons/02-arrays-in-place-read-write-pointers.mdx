<Unit id="read-write-pointers" kind="theory" title="Read/write pointers">

Many "in place" problems keep a **prefix** of the array as the answer and grow it as they scan. Two indices do the work: `read` visits every element; `write` marks where the next kept element goes. Because `write ≤ read` at all times, writing never destroys an element that has not been read yet.

<Callout kind="warn" title="Compare with the last kept value">

`nums[read] !== nums[read - 1]` happens to work on problem 26, because the input is sorted. It fails on the variation "keep at most two copies" (problem 80), where the correct test is `nums[read] !== nums[write - 2]`. Comparing with the kept prefix is the habit that transfers.

Problem 283 keeps the non-zero values in their original order and pushes the zeros to the end. Swapping `nums[read]` into `nums[write]` does both at once: the zero that was at `write` moves to `read`.

<Callout kind="mistake" title="Mistakes to watch for in this lesson">

- `shift()`, `unshift()` or `splice()` inside a loop: each is O(n).
- `new Array(m).fill([])` or `.fill(new Array(n))`: every row is the same array.
- Advancing `write` on every iteration instead of only when an element is kept.
- Returning the array instead of the length `k` on LeetCode's in-place problems.
- `for...in` over an array: it iterates string keys, not values.

</Callout>
