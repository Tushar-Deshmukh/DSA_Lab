<Unit id="the-three-words-that-decide-the-pattern" kind="theory" title="The three words that decide the pattern">

Before any algorithm, read the problem's nouns carefully. Most contiguous-range problems in this module turn on one distinction:

<Include id="theory/two-pointers-windows-prefix-sums/subarray-vs-substring-vs-subsequence" />

Take `[3, 1, 2]`. Its subarrays are `[3] [1] [2] [3,1] [1,2] [3,1,2]`: six, which is n(n+1)/2 for n = 3. Its subsequences also include `[3, 2]`, which skips the 1: there are 2³ = 8 including the empty one. When a problem says "contiguous", "window", "substring" or "subarray", the search space is at most quadratic and a linear pattern is likely. When it says "subsequence", expect exponential brute force and DP or greedy.

<Unit id="intuition-sorted-order-tells-you-which-end-to-throw-away" kind="theory" title="Intuition: sorted order tells you which end to throw away">

You want two numbers from a sorted list that add up to a target. Picture holding the smallest and the largest number. Add them.

- If the sum is **too small**, the smallest number is hopeless: it is already paired with the biggest partner available, and that was not enough. Every other partner is smaller. Throw the smallest number away.
- If the sum is **too large**, the largest number is hopeless for the mirror reason. Throw it away.
- If the sum is exactly right, you are done.

Each comparison removes one number from consideration *forever*, so with n numbers there are at most n − 1 comparisons. Nothing here needs extra memory.

<Unit id="definition-and-the-invariant" kind="theory" title="Definition and the invariant">

**Opposite-end two pointers**: indices `l` and `r` start at the two ends of a sorted (or symmetric) sequence and move toward each other. At every step a rule moves exactly one of them, and the rule is justified by an argument that the element being passed over cannot belong to any answer.

The **invariant** that makes it correct: *if an answer exists, it lies inside `[l, r]`.* It is true at the start (the whole array), and each move keeps it true because the discarded index provably cannot be part of an answer. When `l` meets `r`, the range has no pairs left, so no answer exists.

<Callout kind="key" title="The one sentence to remember">

When `numbers[l] + numbers[r] < target`, `numbers[l]` is too small **even with its largest possible partner** (`numbers[r]`), so no pair using index `l` can work. When the sum is too big, `numbers[r]` is too big even with its smallest partner.

</Callout>

</Unit>

<Unit id="complexity-derived" kind="complexity" title="Complexity, derived">

Count the loop iterations, not the lines. Every iteration either returns or moves one pointer one step inward, so the gap `r − l` shrinks by exactly 1 per iteration. It starts at n − 1 and the loop stops at 0: **at most n − 1 iterations, each O(1), so O(n) time.** The only memory is `l`, `r` and `sum`: **O(1) extra space.**

Compare the alternatives for a sorted input:

| Method | Time | Extra space | Notes |
| --- | --- | --- | --- |
| Brute force, every pair | O(n²) | O(1) | ignores sorted order |
| Binary search for each partner | O(n log n) | O(1) | uses order, but only half of what it tells you |
| Hash map (problem 1) | O(n) | O(n) | needed when input is unsorted |
| Two pointers | O(n) | O(1) | best when input is already sorted |

<Unit id="trade-offs-and-when-not-to-use-it" kind="tradeoffs" title="Trade-offs and when not to use it">

Two pointers needs a reason to discard an end. Sorted order gives one; symmetry (palindromes) gives one. Without it, the moves are guesses. The most important counter-example is the problem you solved in Module 1:

<Callout kind="warn" title="Two Sum (problem 1) is not a two-pointer problem">

The input is unsorted and the answer is a pair of **original** indices. Sorting would cost O(n log n) and scramble the indices, so you would need to sort `[value, index]` pairs and map back. A hash map does it in one O(n) pass. Reach for two pointers when the input is *already* sorted, or when sorting loses nothing you need.

</Callout>

| Situation | Use | Why |
| --- | --- | --- |
| Sorted, find a pair with sum / difference | Two pointers | O(n), O(1) space |
| Unsorted, return original indices | Hash map | sorting would lose the indices |
| Unsorted, return the values, or count pairs | Sort + two pointers, or hash map | both O(n log n) / O(n); two pointers saves memory |
| Need every pair | Neither helps | the output alone is O(n²) |

<Callout kind="mistake" title="Mistakes that cost the most time">

- Writing `while (l <= r)` for a pair search: when `l === r` you pair an element with itself.
- Returning 0-based indices on problem 167, which asks for 1-based ones.
- Skip loops (`while (!isAlnum(s[l])) l++`) without `l < r`: they run off the end on `" .,"`.
- Building a cleaned string with a regex first. It works, but uses O(n) space and is not what interviewers want to see when they ask for O(1).
- Comparing `'0'` and `'P'` case-insensitively by mistake: digits must be kept as they are.

</Callout>

<Unit id="stretch-from-2-sum-to-3sum" kind="stretch" title="Stretch: from 2-sum to 3Sum">

3Sum (problem 15, this lesson's Stretch) reduces to the code above: sort, fix `nums[i]`, then run two pointers on the rest for target `−nums[i]`. The new difficulty is duplicates. After sorting, equal values are adjacent, so skip `i` when `nums[i] === nums[i − 1]`, and after recording a triplet move both pointers past equal values. Complexity: O(n log n) to sort plus n scans of O(n) = **O(n²)**, which is optimal for listing all triplets in the worst case.
