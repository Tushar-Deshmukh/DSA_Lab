<Unit id="the-idea" kind="theory" title="The idea">

<Include id="theory/two-pointers-windows-prefix-sums/sliding-window" />

Brute force over contiguous ranges looks at all O(n²) windows and recomputes each one. A sliding window keeps a **running state** (a sum, a count map, a set) for the current window `[l, r]` and updates it in O(1) when an edge moves. The total work is O(n) because `r` moves n times and `l` moves at most n times, *in total*, not per step.

<Callout kind="key" title="The amortised argument">

An inner `while` inside a `for` loop does **not** automatically mean O(n²). Count how many times `l++` can run over the whole algorithm: `l` only increases and never passes n, so at most n times. The two loops together do at most 2n pointer moves.

</Callout>

</Unit>

<Unit id="variable-size-windows" kind="theory" title="Variable-size windows">

Most window problems ask for the longest or shortest window that satisfies a condition. The window grows until it becomes invalid, then shrinks from the left until it is valid again. The handbook's general template (reference 6.10):

```js
function longestWindow(arr) {
  let l = 0, best = 0;
  const state = new Map();              // whatever describes the window
  for (let r = 0; r < arr.length; r++) {
    // 1. add arr[r] to state
    while (/* window [l, r] is invalid */ false) {
      // 2. remove arr[l] from state
      l++;
    }
    best = Math.max(best, r - l + 1);   // 3. window is valid here
  }
  return best;
}
```

Filling it in is a matter of answering three questions before you code: **What state describes the window? When is the window invalid? What do I record?** For problem 3: state = last index of each character; invalid = the new character already appears inside `[l, r − 1]`; record = `r − l + 1`.

<Unit id="the-precondition-monotonicity" kind="theory" title="The precondition: monotonicity">

A window is allowed to throw away its left end forever only if validity behaves *monotonically*:

- for "longest window with at most …" problems: if `[l, r]` is invalid, then every longer window `[l, r']` with `r' > r` is also invalid, so `l` must move and never needs to come back;
- for "shortest window with at least …" problems: if `[l, r]` is valid, growing it keeps it valid, so once it is valid you shrink to find the minimum.

With non-negative numbers, adding elements never decreases a sum, so sum conditions are monotone. With **negative numbers**, adding an element can decrease the sum, and the rule "grow until too big, then shrink" has no meaning. That is the moment to switch to prefix sums (lesson 5).

<Unit id="validity-as-an-inequality-problem-424-stretch" kind="stretch" title="Validity as an inequality: problem 424 (Stretch)">

Longest Repeating Character Replacement asks for the longest window you can make all-one-letter by changing at most k letters. The cheapest way to make a window uniform is to keep its most frequent letter and change everything else. So the window is **valid while `length − maxCount ≤ k`**.

<Callout kind="tip" title="Why the stale `maxCount` is fine">

The code never decreases `maxCount` when the window shrinks. That makes `maxCount` possibly too large, which can only make an invalid window look valid at the *same length* as the best found so far, never longer. Since we only care about the maximum length, the answer is still right. If that argument feels slippery, recomputing `maxCount` from the 26 counts each step is also O(26n) = O(n).

</Callout>

<Callout kind="mistake" title="Mistakes to watch for in this lesson">

- Shrinking with `if` instead of `while`: the window may still be invalid after one step.
- Recording the answer before the window is valid again.
- Writing the length as `r − l` instead of `r − l + 1`.
- Forgetting the `>= l` check when jumping `l` with a last-seen map (`"abba"`).
- Using a window on input with negative numbers and a sum condition.
